## Apex Conventions

- New Apex test methods use camelCase (PMD `MethodNamingConventions`-compliant), even when surrounding legacy tests in the
  same class use `underscore_separated_names`. camelCase is the target standard; legacy methods will be converted over time.
  Do not match legacy style for new code.
- **USER_MODE for user-triggered automation.** When automation writes records inside an interactive user's transaction, use
  `Database.update(records, System.AccessLevel.USER_MODE)`. System mode makes the automation a confused deputy, writing
  records the invoking user could not otherwise edit. PMD's `ApexCRUDViolation` accepts USER_MODE as satisfying the rule.
  Pair it with FLS-aware reads so the whole path is least-privilege end to end.
- Automation that fires inside an interactive user's transaction must never block that user's primary action. Log and
  continue on failure rather than throwing.

## Static Analysis (PMD / Gearset)

- The Gearset PMD ruleset is exported to the repo root as `pmd_gearset_standard_ruleset.xml`. Run static analysis locally
  before promoting anything through the Gearset pipeline:

  pmd check -d unpackaged/main/default/classes -R pmd_gearset_standard_ruleset.xml -f text

- Local PMD must be at or above the version Gearset uses (Gearset: 7.27.0). An older PMD fails to load the ruleset
  entirely — a single unresolvable rule reference aborts the whole file, so it fails loudly rather than degrading.
- The export contains only *activated* rules (verified 1:1 against the Gearset UI toggles), so it requires no editing. It
  must be re-exported whenever a rule is toggled in Gearset.
- Always run with the exported ruleset, not PMD's default categories. Gearset's thresholds differ from PMD defaults in
  places — e.g. `NcssMethodCount` is set to 60, not the default 40 — and several rules are deactivated, so default
  categories produce phantom findings.
- Four rules in the ruleset emit PMD 8 deprecation warnings (`ExcessiveClassLength`, `NcssConstructorCount`,
  `NcssMethodCount`, `NcssTypeCount`). Non-fatal; they appear with an ⓘ marker in the Gearset UI.

### Static-analysis cleanup workflow

Default order when addressing findings:
1. Fix every finding introduced by the current change.
2. Fix trivially-safe pre-existing findings (braces, naming conventions, missing ApexDoc tags on unambiguous methods).
3. Report the remaining findings for triage rather than fixing them unilaterally — complexity refactors, SOQL-injection
   review, and CRUD/FLS decisions need case-by-case judgment.

Verify line numbers against the actual code before acting on a report. Inserting code shifts line numbers, so pre-existing
findings often appear to be new.

## Gearset Pipeline

- Gearset auto-selects tests that appear in the commit's git diff, or that match the `<ClassName>Test` naming convention. It
  also supports manually adding test classes.
- A class with no same-named test class will under-report coverage and can fail the 75% gate even when real coverage is
  high. To find the right tests, query per-test attribution from the `ApexCodeCoverage` tooling object (aggregate the union
  of `Coverage.coveredLines` per `ApexTestClass`), then supply the manual list.
- Do not validate with a narrow, hand-picked test selection without checking coverage first.
- A new custom field referenced by an Apex class must deploy in the same set as that class, or the class will not compile.
  Confirm Gearset has not filtered custom-setting fields out of the changeset.

## Key Codebase Knowledge

- **IA ↔ Case linkage.** `IndividualApplication.ApplicationCaseId` is used for all Charitable cases. Class comments
  claiming the reverse direction is "intentionally not used" were stale and have been removed.
- **`ApplicationCaseId` is sparsely populated.** CEO-2321 stamps it only when the Case-side link
  (`Case.IndividualApplication__c`) is set or changed, so records linked before CEO-2321 deployed were never backfilled. In
  dev, 4 of 6 linked Charitable Cases have it null. This is expected legacy data, not a defect: the back-pointer was
  implemented recently and existing records were never backfilled. New automation should still key on `ApplicationCaseId`,
  but be aware it will silently no-op for pre-implementation records until a backfill is run.
- **Charitable Case status graph.** There is no `Submitted → Awaiting Nonprofit Application` edge. Only
  `In Progress → Awaiting Nonprofit Application` is legal (`BOD_CaseDomain.buildTransitionGraph`).
  `Submitted → In Progress` is additionally gated by `enforceAssignmentBeforeProgress`, which blocks the move while the Case
  is still queue-owned (OwnerId prefix `00G`).
- **Case trigger stamps queue ownership on insert.** Every new BOD Case is defaulted to its per-type "Unassigned" queue, so
  test helpers that insert a Case and then advance it to In Progress must set
  `BOD_CaseDomain.skipAssignmentBeforeProgressCheck = true`.
- **`Case.Status` has field history tracking enabled**, so status-change auditability requirements are satisfied natively
  with no extra work.
- **Reaching "Awaiting Nonprofit Application" has no side effects** — no ledger row (value is committed at Submitted) and no
  automated notification. A status-only write to that value is genuinely surgical.
- **FLS caution in `BOD_CaseSelector`.** `getByIds` queries ~11 `BOD_*` fields under `WITH USER_MODE`; a single missing FLS
  grant fails the entire read. For automation that only needs lifecycle state, use the lean `getStatusByIds` (Id, Status,
  RecordTypeId) to minimize the FLS surface.
- **`Account.SGV_Nearest_Station__c`** — API name says "Nearest Station," but the label reads "Southwest Gives Closest
  City." It is a lookup to the standard `Location` object representing the nearest SWA station, not free text. The
  name/label mismatch is a trap when working from the UI label.
- **`IndividualApplication` status `Invited` cannot be set by direct field edit.** The `SGV_Only_Allow_Invite_Email_IA`
  validation rule requires the "Invite Partner" button. Data Loader or manual status edits will be blocked.
- **Trigger framework.** Org-wide triggers route through `ORG_TriggerContext.handle(...)` with a per-object
  `ORG_Control_<Object>__c` custom setting carrying `Trigger_Disable_*` / `Validation_Disable_*` / `Flow_Disable_*` kill
  switches. Follow this pattern and add a named kill switch for new automation.
