### Deploy behaviour

- **Scope `sf project deploy validate` to the changed files, never `--source-dir .../classes`.**
  Validate enforces the 75% per-class coverage gate on every class in the package, and this org
  has many classes well under it (several at 0%). A whole-directory validate fails on those
  pre-existing gaps and tells you nothing about your change. `deploy start` with specific files
  does not trip this.
- **Apex and the Experience Cloud front end are separate deploys.** Apex lives in
  `force-app/main/default/classes`; the React app is the `SWAGivesCommunityBuilder` uiBundle
  (~227 components). Shipping a scoring change means deploying both, otherwise the tooltip and
  the ranking disagree in the live org.
- **The uiBundle must be rebuilt (`npm run build`) before deploying**, and the emitted
  `dist/assets/index-*.js` is content-hashed, so a new file appears and the old one must be
  staged as deleted. `node_modules` is absent on a fresh clone; `npm ci` in the bundle directory
  is required before `npm run build` or `npx vitest run` will work.
- **Deploying the uiBundle does not prune resources that disappeared.** Stale hashed assets from
  earlier deploys stay in the org (unreferenced by `index.html`, so harmless but accumulating).
  Use `sf project delete source` to clean them up.
- **Asset hashes differ between build machines for byte-identical content.** `brush-stroke-*.svg`
  and `nav-active-outline-*.svg` flip-flop names between contributors' builds. Verify with
  `shasum` before assuming a real change; the bundle stays internally consistent either way.

## Apex Conventions

- New Apex test methods use camelCase (PMD `MethodNamingConventions`-compliant), even when surrounding legacy tests in the
  same class use `underscore_separated_names`. camelCase is the target standard; legacy methods will be converted over time.
  Do not match legacy style for new code.
- **USER_MODE for user-triggered automation.** When automation writes records inside an interactive user's transaction, use
  `Database.update(records, System.AccessLevel.USER_MODE)`. System mode makes the automation a confused deputy, writing
  records the invoking user could not otherwise edit. PMD's `ApexCRUDViolation` accepts USER_MODE as satisfying the rule.
  Pair it with FLS-aware reads so the whole path is least-privilege end to end.
- Automation that fires inside an interactive user's transaction must never block that user's primary action. Log and
  continue on failure rather than throwing.

## Key Codebase Knowledge

### SGV volunteer portal (SWAGives)

- **Geocoding is tiered in `SGV_GeoService`**: `SGV_Zip_Centroid__mdt` (zip, then city centroid)
  -> `SGV_Geocode_Cache__c` -> OSM Nominatim callout via the `SGV_Nominatim` Named Credential.
  Use `locateLocal()` in trigger context because it never calls out; `locate()` and
  `locatePlace()` may call out and are safe only from async or request context.
- **Nominatim is governed by the OSMF usage policy** (https://operations.osmfoundation.org/policies/nominatim/).
  Binding constraints: max 1 request/second for the whole application (not per user), a
  descriptive `User-Agent` is mandatory, every result must be cached, autocomplete and
  systematic/bulk querying are forbidden, and the provider must be switchable without a code
  change. Provider config therefore lives in `SGV_Geocode_Setting__mdt`, not in Apex. Never wire
  geocoding into a keystroke-triggered search path, and keep backfills single-threaded
  (`Database.executeBatch(new SGV_GeocodeBackfillBatch(), 1)`).
- **Event coordinates are populated by `SGV_EventTrigger`**, not by the REST layer, so every
  write path gets them. Explicitly supplied coordinates are never overwritten by a centroid.
  `SGV_TestUtil.event()` pre-sets `SGV_Location__*`, so a test that wants to exercise resolution
  must null those fields first.
- **Event match weights are proximity 40, interest 25, availability 15, keywords 15, capacity 5.**
  Nonprofits are type overlap 45, keywords 30, proximity 25. Proximity deliberately outranks
  interest for events, so a convenient event in an unpicked category can beat a loved one past
  twice the radius. Both sets must sum to 100 because `SGV_Scoring.total()` renormalises against
  it; `SGV_ScoringTest.eventWeightsSumToOneHundred` enforces that.
- **Proximity scoring plateaus**: full weight anywhere inside the Coheart's preferred radius,
  then linear decay to zero across a band one radius wide (zero at 2x radius). A preferred
  radius is a threshold, not a gradient. Remote events always take the full proximity weight.
- **`Breakdown.proximity` is nullable and null means "distance unknown", which is not zero.**
  `SGV_Scoring.total()` drops proximity and rescales the remaining weights to 100 in that case.
  Consequence: breakdown components do not always sum to `score`. An explicit `maxDistanceMi`
  filter excludes unknown-distance records rather than letting them through.
- **`SGV_Scoring.total(b)` grades an EVENT; nonprofits must call `total(b, N_PROXIMITY)`.** The
  renormalising branch subtracts the applicable proximity weight from 100, and events (40) and
  nonprofits (25) differ. Passing the wrong one silently inflates or deflates every score whose
  distance could not be resolved — no error, just wrong numbers.
- **Event scoring weights are duplicated in the front end** at
  `uiBundles/SWAGivesCommunityBuilder/src/lib/match.ts` (`WEIGHTS`), which divides each
  breakdown part by its own weight for the tooltip. Nothing keeps it in sync with `SGV_Scoring`,
  and it has drifted before, showing proximity clamped at 100% and a full interest hit as 63%.
  Change both together, and remember the Apex and the uiBundle are separate deploys.
- **`SGV_SearchFilters.remoteRequested` is exclusive, not a widening override.** When true the
  search returns remote events ONLY: it lets them through for a Coheart who opted out in their
  profile AND filters out every event that requires travel. "Virtual events only" previously
  returned a mix. The tradeoff is that a false positive from the model or parser hides all
  in-person events, so the agent-facing descriptions warn against setting it for text that
  merely allows remote. A Coheart who would take either kind must not mention remote at all.
  Nonprofit search ignores the flag.
- **`Account.RecordType.DeveloperName = 'Nonprofit'` gates nonprofit search.** Any nonprofit
  account loaded without that record type is invisible to search while still being referenced by
  events. Check it after any Account data load.
- **`SGV_Volunteerism_Event__c.SGV_Account__c` is a Lookup with `deleteConstraint = SetNull`.**
  Deleting a nonprofit silently orphans its events instead of failing, so audit child events
  before deleting any Account.
- **External-id prefixes must match across data loads.** `SGV_External_Id__c` is unique and an
  external id, so upsert dedupes correctly only when the prefix is stable. A load that reused the
  numeric sequence under a different prefix (`EV-200` vs `SWG-EV-200`) inserted parallel records
  instead of updating, producing apparent duplicates that were in fact distinct events.
- **Deleting a nonprofit Account has three child dependencies, not one.** `SGV_Volunteerism_Event__c`
  and `SGV_Nonprofit_Favorite__c` both reference it, and events cascade to
  `SGV_Volunteer_Enrollment__c`. Favorites *restrict* the delete and produce
  `DELETE_FAILED: ... associated with the following sgv nonprofit favorites`, whereas the event
  lookup is `SetNull` and silently orphans instead. Audit events AND favorites before deleting.
- **Remote events legitimately have no coordinates.** `SGV_Is_Remote__c = true` events carry no
  city, state or zip, so `SGV_Location__c` is null and `SGV_EventTrigger` leaves them alone by
  design. When auditing unplaced events always filter `AND SGV_Is_Remote__c = false`, otherwise
  remote events read as a geocoding failure.

### Agentforce agent versions (SWAGives Volunteer Guide)

- **A published `AiAuthoringBundle` version is immutable.** Editing the `.agent` script and
  redeploying fails with `content cannot be changed once the bundle version is published`.
  Deactivating the version does NOT unlock it. The only path is a new version.
- **Creating a new agent version via metadata, in this order:**
  1. Deploy a new `AiAgentDefinitionVersion` (e.g. `MyAgent#2`): copy the previous folder, bump
     `<version>`, rename `genAiPlannerName`/`planner.fullName` to `_v2`, delete the
     `<agentScript>` and `<agentGraphRef>` id elements so the platform regenerates them, and make
     the `instruction0_*` `developerName` values unique. Status must be `Active` or `Inactive`;
     `Draft` is rejected with `'Draft' is not a valid value for the enum 'BotStatusCode'`.
  2. Then deploy an `AiAuthoringBundle` whose `<target>` is `MyAgent.v2`. Doing this first fails
     with `no BotVersion named MyAgent.v2 found`, because the bundle attaches to an existing
     version.
  Deploying as `Inactive` stages the version without taking traffic, then it can be activated in
  Agent Builder.
- **`SGV_Agent_Setting__mdt.SGV_Agent_Id__c` holds the BotDefinition id, not a version id.**
  Activating a new version therefore changes behaviour for BOTH chat and the Events page, since
  `SGV_EventSearchResource` -> `SGV_AgentApiClient.extractFilters` calls whichever version is
  active. Verify the `filter_extraction` subagent is intact in any new version.
- **Never let an Agentforce action call the Agent API.** `SGV_EventSearchAction` is invoked by the
  same agent that `SGV_Agent_Setting__mdt` points at (one `BotDefinition` row), so extracting
  filters inside the action re-enters that agent. It only terminated because the router sends
  anything starting with "Extract volunteer search filters" to a subagent that declares no
  actions, which is a prompt-level guarantee, not a code one. Each nested call is a separate Apex
  transaction, so per-transaction limits never catch the recursion. The action takes structured
  filter inputs instead and falls back to `SGV_QueryParser` for text-only requests. The
  regression test registers no `HttpCalloutMock`, so any reintroduced callout fails the test.
- **Action inputs use semicolon-delimited text, not `List<String>`.** The action's JSON schema
  then needs only `lightning__textType`, avoiding an unverified array schema shape that would
  fail silently at runtime. Split with `SGV_CoheartMapper.splitMulti`.
- **Bound anything a model supplies** through `SGV_SearchFilters.sanitize()`, shared by the action
  and `SGV_AgentApiClient.parseFilterJson`. An invented interest name, a 9000 mile radius or an
  unparseable date must degrade the search, never corrupt it. A null `Boolean` action input means
  "not supplied" and must not read as `true`.
