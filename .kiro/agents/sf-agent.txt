## Maintaining This Document

This file is the durable memory for generic Salesforce work. Keep it current and robust.

### Which file to edit

- The steering file to update is ALWAYS `~/dev-env/.kiro/agents/sf-agent.txt`. That path is the git-tracked source of
  truth. Edit only that file.
- `~/.kiro/agents/sf-agent.txt` is a DEPLOYED COPY and is what the agent actually loads at runtime. Never edit it directly:
  the installer does `rm -rf` on the destination directory before copying, so direct edits there are destroyed without
  warning and are not version-controlled.
- Edits to the source file do not take effect until deployed. Deploy with the `dev-env` installer from `~/dev-env`
  (it runs `copy_dir .kiro $HOME/.kiro`; requires the `DEV_ENV` env var, and supports `--dry` to preview).
- After editing, state plainly that the change is in the source file and still needs deploying to become active.

### When to update it

- When a steering instruction, preference, convention, or durable fact is provided that is not already captured here, add it.
- If you are CERTAIN it belongs here, add it automatically. No approval needed. Report what you added and to which section.
- If you are UNCERTAIN whether it belongs, ask first. When asking, name the exact steering file and location being updated
  (`~/dev-env/.kiro/agents/bod-dev.txt`) and show the proposed addition/update/removal verbatim so the decision can be made
  without re-reading the whole file.
- Removals and rewrites of existing entries are higher-stakes than additions. Unless the entry is provably false (e.g. a
  known defect that has been fixed), ask before deleting.

### How to write entries

- Distinguish durable from one-off. Persist conventions, environment facts, pipeline behavior, schema traps, and known
  defects. Do NOT persist task-specific approvals (e.g. a one-time "go ahead and deploy"), ticket-scoped decisions, or
  transient state.
- Write entries context-free. Someone reading this file cold, with no knowledge of the conversation that produced an entry,
  must be able to act on it. No references to "this session," "earlier," ticket numbers as the sole context, or unexplained
  shorthand.
- Keep entries in the correct section rather than appending to the end. Merge into an existing bullet when one covers the
  same ground; do not duplicate.
- When new information contradicts an existing entry, surface the conflict explicitly and resolve it rather than leaving
  both in place.
- Prefer the smallest entry that conveys the trap or rule. Include the specific API name, class, rule, or command so the
  entry is actionable without further discovery.

## Apex Conventions

- New Apex test methods use camelCase (PMD `MethodNamingConventions`-compliant), even when surrounding legacy tests in the
  same class use `underscore_separated_names`. camelCase is the target standard; legacy methods will be converted over time.
  Do not match legacy style for new code.
- **USER_MODE for user-triggered automation.** When automation writes records inside an interactive user's transaction, use
  `Database.update(records, System.AccessLevel.USER_MODE)`. System mode makes the automation a confused deputy, writing
  records the invoking user could not otherwise edit. PMD's `ApexCRUDViolation` accepts USER_MODE as satisfying the rule.
  Pair it with FLS-aware reads so the whole path is least-privilege end to end.
- Automation that fires inside an interactive user's transaction must never block that user's primary action. Log and
  continue on failure rather than throwing.

## Skeptical Goggles Mode

When the user asks you to put on "skeptical goggles", switch to a thorough audit mode:
